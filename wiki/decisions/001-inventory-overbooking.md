# ADR-001: 재고·오버부킹 모델 (특정방 vs 호텔형)

- **상태:** Accepted
- **날짜:** 2026-09-25
- **맥락:** 예약/재고 설계 방향. 에어비앤비형 특정방과 호텔형 객실 풀은 재고·오버부킹 규칙이 달라야 한다.

## 결정

시스템을 **두 가지 판매 모드**로 나눈다. 같은 “방 1개”라도 모드에 따라 재고·오버부킹·배정 시점이 다르다.

### 1) 특정방 예약 (Airbnb-like)

| 항목 | 규칙 |
|------|------|
| 판매 단위 | **특정 객실 1개** (호수/유닛이 예약 시점에 확정) |
| 재고 | 카운트 풀이 필요 없음. 해당 유닛·날짜에 **가능 / 불가** 이진 |
| 오버부킹 | **허용하지 않음** |
| 배정 | 예약 생성 시점에 이미 배정 완료 |

**의도:** 게스트가 “그 방”을 산 것이므로, 이중 판매는 곧바로 약속 위반이다.

### 2) 호텔형 (room type pool)

| 항목 | 규칙 |
|------|------|
| 판매 단위 | **객실 타입(룸타입)** — 같은 타입 N실의 풀 |
| 재고 | 날짜별 `available = capacity − confirmed − held` 형태의 **카운트** |
| 오버부킹 | **조건부 허용** (아래 게이트 모두 통과할 때만). 노쇼·취소를 전제 |
| 배정 | **입실(체크인) 시점에 호수 확정**. 예약 시점에는 타입만 확정 |

**의도:** 호텔은 예약 = “더블룸 1박”이지 “205호”가 아니다. 취소를 감안해 풀을 약간 넘기면 점유·매출을 지킬 수 있다. 다만 **임박 일자**나 **풀이 작은 타입**에 오버북하면 취소가 안 나와도 흡수할 여유가 없어 사고로 이어진다.

#### 오버부킹 허용 게이트 (호텔형만)

세 조건을 **모두** 만족할 때만 capacity 초과 판매를 허용한다. 하나라도 안 되면 오버북 비율 = 0 (capacity까지만).

**원칙: 경험 리스크 우선, 보수적으로.**  
오버북으로 점유·매출을 조금 더 가져가는 이득보다, **실방 부족 → 입실 실패·보상·리뷰 악화** 비용이 훨씬 크다. 특히 무인·앱 체크인에서는 프론트에서 “다른 방으로 안내”가 어렵다. 따라서 기본값은 **좁게(오버북 잘 안 되게)** 두고, 운영이 데이터를 보며 어드민에서만 풀어 올린다.

| 게이트 | 규칙 | 기본값 / 열린 질문 | 이유 |
|--------|------|-------------------|------|
| **기간** | 체크인까지 남은 일수가 **`min_lead_days` 이상**일 때만 | **어드민 설정.** 후보: `2`? `3`? `그 이상`? — **D+3도 위험할 수 있음 (?)** . 확정하지 않고 설정으로 둔다. 기본값은 **더 보수적인 쪽**(예: 3 이상)을 권장 | 임박일일수록 취소·노쇼가 나올 시간이 없고, 대체·업셀도 어렵다 |
| **규모** | 해당 룸타입 capacity ≥ **`min_capacity_for_overbook`** | **어드민 설정.** 초기 가정 `10` (역시 올려서 더 보수적으로 가능) | 작은 풀은 10%도 1실 단위 사고로 이어짐 |
| **비율** | 초과분 ≤ capacity × **`overbook_rate`** | **어드민 설정.** 초기 가정 `≤ 10%`, 필요하면 더 낮게. 내림하여 정수 실 | 취소율 가정의 상한. 매출 욕심으로 기본을 올리지 않음 |

```
# 세 값은 코드 상수가 아니라 Admin(지점/룸타입) 설정
if mode == HOTEL_POOL
   and days_until_checkin >= min_lead_days        # admin
   and capacity >= min_capacity_for_overbook      # admin
   and overbook_rate > 0:                         # admin, 0이면 사실상 비활성
     max_sellable = floor(capacity * (1 + overbook_rate))
else:
     max_sellable = capacity
```

**예시** (`min_lead_days = 3`으로 가정한 경우 — 수치 자체는 ?)

- capacity 20, D+5 → 게이트 통과 → max 22 (10%)
- capacity 20, **D+1 / D+2 / (설정에 따라 D+3)** → 기간 게이트 실패 → max 20
- capacity **5**, D+10 → 규모 게이트 실패 → max 5
- 특정방 모드 → 게이트 없음, 항상 1 또는 0
- 어드민에서 `overbook_rate = 0` → 호텔형이어도 오버북 완전 비활성 (가장 보수적)
## 왜 이렇게 나누나

- 특정방에 호텔식 오버북을 허용하면 **그 방을 산 게스트**를 배신한다.
- 호텔형에 특정방처럼 오버북 0을 강제하면, 취소·노쇼를 못 흡수해 **불필요하게 낮은 점유**가 된다.
- 배정 시점이 다르면 데이터 모델도 달라진다.
  - 특정방: `reservation → room_unit` (즉시)
  - 호텔형: `reservation → room_type` (예약) → `room_unit` (체크인)

## 아직 안 정한 것 (다음에 채울 예정)

- [x] 임박 일자 오버북 금지 → `min_lead_days` **존재** (정확한 숫자는 ? — D+2만? D+3도 위험?)
- [x] 소규모 풀 오버북 금지 → `min_capacity_for_overbook` **존재**
- [x] 게이트 수치 → **어드민에서 조정** (코드 하드코딩 금지). 기본은 보수적
- [ ] `min_lead_days` 권장 기본값 확정 — **3 이상?** 운영 데이터(취소 분포) 보고 결정
- [ ] 설정 단위: **전역 / 지점 / 룸타입** 중 어디까지 내릴지
- [ ] 이미 오버북된 재고가 있는데 날짜가 임박해졌을 때 — **신규 판매만 차단** vs 기존분 축소/알림
- [ ] `held`(결제 전 임시 점유) TTL과 확정(`confirmed`) 전환
- [ ] 오버북으로 실제 방이 모자랄 때의 **업셀/이동/보상** 플로우 (경험 리스크의 최후 방어)
- [ ] 어반스테이(생숙)가 운영상 어느 모드에 가까운지 — 유닛 확정형인지 타입 풀인지
- [ ] 멀티 OTA 채널에서 모드별 재고 동기화 규칙

## 결과 (구현에 미치는 영향)

- 재고 API/도메인을 하나로 뭉개지 말고, **판매 모드(enum)** 로 분기한다.
- 오버부킹 검사는 호텔형에만 존재하고, **기간·규모·비율** 게이트를 통과할 때만 `max_sellable > capacity`.
- `min_lead_days`, `min_capacity_for_overbook`, `overbook_rate`는 **어드민 설정값**. 기본값은 보수적으로(리드타임 길게, 최소 규모 크게, 비율 낮게 또는 0).
- 특정방은 **유니크 제약(유닛 × 날짜 구간)** 으로 막는다.
- 체크인 배정 로직은 호텔형 전용이다.
- 수치를 “맞춰서 매출 최적화”하기보다, **경험 사고가 안 나는 범위에서만** 풀어 올린다.

## 참고

- 업계: OTA 멀티채널에서 수동 마감 누락 → 오버부킹이 흔함. 특정방 모드는 이 리스크를 설계로 차단하는 쪽이 맞다.
- 핸디즈 맥락: 무인·앱 체크인이므로, **배정이 늦어지거나 실패하면** 키 발급·입실 readiness와 바로 연결된다 (후속 ADR에서 다룸).
