# 결제·정산·멱등성 — 정책서

근거: 토스 PO Session · RARRA · 문제 해결사 17질문  
스콥 합의: **게스트 결제(A) + 오너 정산(C)** · 다이렉트 즉시 전액 + **OTA는 채널 정산(D)**  
기술 세부(키 포맷·아웃박스·PG 어댑터)는 후속 **ADR**(결제·멱등성)로 분리. 본 문서는 **제품·도메인 규칙**만 고정한다.

## 한 줄 성공 정의

> 게스트가 다이렉트 예약 시 **이중청구·미결제 확정 없이** 한 번만 결제되고, 오너가 월말에 **같은 숙박을 두 번 세지 않은** 정산액을 받아 “위탁해도 돈이 맞는다”는 신뢰를 유지한다. (이중청구 건수 → 0, 정산 불일치 티켓 → 0에 가깝게.)

---

## 1. Identify — 문제 (PON)

### Problem

예약만 있고 **결제·정산 규칙이 없으면** 재고 `held`가 영원히 남거나, 재시도로 **이중청구**, 오너에게는 **같은 매출이 두 번** 잡힌다.

- 게스트: 네트워크 재시도·뒤로가기·앱 재진입 → “결제됐는지” 불명 → CS·환불 분쟁 (후보 #5·#6 인접).
- 오너: 월 정산이 늦거나 숫자가 안 맞으면 위탁 신뢰 붕괴 (후보 #8).
- 운영: OTA는 손님이 채널에 내고, 다이렉트는 우리가 받는데 **한 리포트에 섞으면** 인식 기준이 흔들림.

증상은 “결제 문의·정산 재작업”. 근본은 **돈의 단위(PaymentIntent)와 예약·재고 전환이 멱등하지 않고, 오너 정산 인식 시점이 정의되지 않은 것**.

### Opportunity

- **Revenue 가드레일:** 결제 실패인데 `confirmed`가 되거나, 성공인데 `held`만 남는 사고를 제거 → 체크인 Activation 전제(유료·유효 예약) 강화.
- **Supply(오너) 신뢰:** 정산이 맞으면 위탁 유지·확장. RARRA의 Referral/Revenue보다 **공급 리텐션**에 가깝다.
- ADR-001의 미결 `held` TTL · `confirmed` 전환을 **결제 성공 = 확정**으로 닫을 수 있다.

### Needs (JTBD)

| Who | JTBD |
|-----|------|
| 게스트 | “한 번만 내고, 예약이 확정됐는지” 분명히 알고 싶다 |
| 운영 | 재시도·채널 차이가 있어도 장부가 안 틀리게 맞추고 싶다 |
| 오너 | 이번 달 내 자산에서 나온 숙박 매출을 **빠짐·중복 없이** 받고 싶다 |

### 5 Whys

1. 왜 이중청구·정산 불일치가 나나? → 같은 의도(Intent)가 여러 번 실행되거나, 인식 시점이 채널마다 다름.
2. 왜 Intent가 여러 번 실행되나? → 재시도에 **같은 키로 같은 결과**를 주는 규칙이 없음.
3. 왜 재고·예약 상태가 돈과 어긋나나? → `held→confirmed`가 결제 성공과 원자적으로 묶이지 않음.
4. 왜 오너 숫자가 안 맞나? → 다이렉트 즉시수금 vs OTA 후정산을 **같은 “매출일”**로 취급.
5. **근본 원인:** **결제 Intent 멱등성**과 **정산 인식(recognition) 규칙**이 제품 정책으로 고정되지 않음.

## 6. Execute — 실험 설계

- **Hypothesis:** Intent 멱등 키 + `결제 성공 시에만 confirmed` + 오너 정산 recognition을 고정하면, 재시도·웹훅 중복 시나리오에서도 이중청구·이중정산이 0이 된다.
- **Metric:** 의도적 재시도 테스트 N회 중 청구 횟수=1 · 불일치 건수=0 · 정산 라인에 reservation_id 유일
- **Next action if true:** PRD 시나리오·ADR(결제 멱등) Accepted → 구현 우선순위 다이렉트 MVP
- **Next action if false:** 키 범위(예약 vs 세션) 또는 정산 인식 시점(체크아웃 vs 결제월)을 바꾼 뒤 재실험

## 8. 가정 / 위험 가정

- 가정: 통화 **KRW**, 금액 정수(원). 세금/봉사료는 과제에서 라인 구분만 가능하면 되고 세율 엔진은 없음.
- 가정: **한 예약 = 하나의 주결제 Intent**(전액). 체류 중 추가결제(주차·얼리CI 등)는 **별도 Intent**, 같은 멱등 규칙을 따름.
- 가정: OTA 예약은 채널이 수금. 우리 DB에는 `payment_source = OTA` + 채널 정산 예정/입금 상태만 둔다.
- 가정: 오너 정산 주기 = **달력월**. 지점(property) 단위 집계.
- 위험 가정 (#15): 모의 PG로 웹훅 중복·타임아웃 재시도를 충분히 재현할 수 있다.
- 검증 방법: 실패 주입 테스트 매트릭스(아래 도메인 규칙 §G) + 샘플 정산 CSV/화면.

## 9. 도메인 규칙 (정책 본문)

이 섹션이 **제품이 지키는 계약**이다. 구현 세부는 ADR.

### A. 채널별 돈의 흐름 (D 확정)

| 채널 | 게스트 결제 | 예약 확정 조건 | 오너 정산 인식 |
|------|-------------|----------------|----------------|
| **다이렉트** | 예약 확정 = **즉시 전액** 결제 성공 | `PaymentIntent(CHARGE)` **Succeeded** | 해당 숙박의 **정산 대상 금액**을 월 정산에 포함 (아래 C) |
| **OTA** | 채널 수금. 우리는 결제 API 호출 안 함 | 채널 확정 웹훅/동기화 + 재고 규칙(ADR-001) | **채널 입금(또는 확정된 채널 정산액)** 기준으로 인식. 미입금 월에 오너에게 선지급하지 않음 (가정) |

### B. 예약·재고·결제 상태 (ADR-001 연동)

| 재고 | 예약 | 결제 (다이렉트) | 규칙 |
|------|------|-----------------|------|
| `held` | `PENDING_PAYMENT` | Intent `RequiresAction` / `Processing` | 결제 전 임시 점유. **TTL** 초과 시 held 해제·예약 `EXPIRED`·Intent `Cancelled` |
| `confirmed` | `CONFIRMED` | Intent `Succeeded` | **결제 성공과 동시에만** 전환. 결제 없이 confirmed 금지 |
| (해제) | `CANCELLED` / `EXPIRED` | — | held/confirmed 재고 복구는 ADR-001·취소 정책 |

**held TTL (가정, 수치 확정은 ADR/어드민):** 다이렉트 결제 세션 **15분**. TTL과 Intent 만료는 같게 맞춤.

추가결제(체류 중): 재고를 다시 held 하지 않음(이미 입실). Intent만 생성·멱등.

### C. 오너 정산 recognition

| 항목 | 규칙 |
|------|------|
| 집계 단위 | `property_id` × `yyyy-MM` |
| 다이렉트 포함 조건 | 숙박의 **체크아웃 일**이 해당 월에 속하고, 주결제가 `Succeeded`이며, 환불·취소로 **순액 > 0**인 라인 |
| OTA 포함 조건 | 채널 **정산 입금이 우리 장부에 Posted**된 금액만. 체크아웃 월 ≠ 입금 월일 수 있음 → **입금 월**에 인식 (현금주의에 가깝게. 가정) |
| 환불 | 환불 Intent `Succeeded` 시 해당 예약 라인을 **차감**(같은 월이면 순액 감소, 익월이면 음수 조정 라인) |
| 수수료 | 플랫폼/OTA 수수료는 라인으로 구분. 오너 지급액 = 합의 분배 규칙(가정: 과제에서는 **고정 %** 또는 “전액−수수료” 한 줄) |
| 중복 금지 | 같은 `reservation_id`(+ `payment_intent_id`)가 한 정산 런에 **두 번 집계되면 실패** |

정산 런 자체도 멱등: `settlement_run_key = property_id + period + policy_version`. 동일 키 재실행 → 같은 결과 재사용(또는 no-op).

### D. 멱등성 (제품 규칙)

| 대상 | Idempotency-Key 범위 (논리) | 재시도 시 기대 |
|------|------------------------------|----------------|
| 다이렉트 청구 | `reservation_id` + `purpose=CHARGE_FULL` | 이미 Succeeded면 **재청구 금지**, 동일 성공 결과 반환 |
| 추가결제 | `reservation_id` + `purpose` + `order_line_id` | 라인당 1회 성공 |
| 환불 | `reservation_id` + `cancel_or_refund_event_id` | 동일 환불 1회 |
| OTA 입금 전기 | `channel` + `channel_payout_id` | 같은 입금 두 번 Posted 금지 |
| 오너 정산 런 | `property_id` + `period` + `policy_version` | 동일 리포트 |

**금지:** 클라이언트 랜덤 UUID만으로 키를 만들고 매 탭마다 새로 발급 → 이중청구. 키는 **비즈니스 Intent**에 고정.

**웹훅/콜백:** PG·채널이 같은 이벤트를 N번 보내도, 내부는 Intent 상태머신상 **한 번만 전이**. 이미 최종 상태면 ack만.

### E. 실패·경계

| 상황 | 동작 |
|------|------|
| 결제 실패/거절 | 예약 `PENDING` 유지 또는 실패 카운트 후 EXPIRED. **confirmed 금지**. held는 TTL까지 유지 가능(재시도 허용) |
| 타임아웃 후 실제 성공 웹훅 | Intent를 Succeeded로 맞추고 confirmed. 이미 EXPIRED였으면 **자동 환불 Intent** 또는 운영 큐 (가정: 과제에서는 “불일치 큐”로 표시) |
| 취소(체크인 전) | 환불 정책 버전 적용(가정: 전액/일부 — 상세 %는 PRD). 재고 복구 + 정산 차감 |
| 노쇼 | 다이렉트: 결제 유지(가정) + 재고 해제. 오너 정산에는 포함 |
| OTA 미입금 | 오너 월 지급에 **포함하지 않음**. 대시보드에 “미입금” 노출 |

### F. 모듈 경계 (ADR-002 정합)

- 결제 Intent·상태머신: booking(또는 얇은 `payment` 포트) — **inventory는 결제 성공 신호로만 confirmed 전환**
- 오너 정산: 별도 집계 서비스/모듈 후보. YAGNI로 시작해도 **키·recognition 규칙은 본 정책 준수**
- 채널 입금: `channel` 모듈이 payout 이벤트 발행 → 정산이 consume

### G. 검증 시나리오 (실험 매트릭스)

1. 결제 버튼 5연타 → 청구 1
2. 성공 응답 유실 후 재요청 → 청구 1, confirmed 1
3. 웹훅 3중복 → 전이 1
4. TTL 만료 후 늦게 온 성공 → 불일치 큐 또는 자동환불 (구현 선택, 정책상 **silent confirmed 금지**)
5. 동일 월 정산 런 2회 → 결과 동일, 지급 지시 1
6. OTA 예약이 다이렉트 CHARGE Intent를 만들지 않음
