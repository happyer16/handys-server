# CMS·체크인 운영 코어 — 정책서

근거: 토스 PO Session · RARRA · 문제 해결사 17질문  
Plott OS 매핑: **01 CMS** · **04 스마트 체크인** (재고·예약 PMS 코어 포함)  
후순위 TODO: **08 스마트 프라이싱** · **05 주차·결제 부가**

## 한 줄 성공 정의

> 운영자·시스템이 채널 재고를 ADR-001 규칙으로 막은 뒤, 게스트가 체크인 시각에 **키·본인확인·객실 Ready가 모두 Go**인 상태로 입실에 성공하는 비율이 올라간다. (오버부킹으로 인한 입실 실패·키 미발급이 줄고, 무인 Activation이 성립한다.)

---

## 1. Identify — 문제 (PON)

### Problem

무인·앱 운영에서 **팔 수 있는 재고**와 **입실 가능한 상태**가 끊기면 사고가 난다.

- **CMS 쪽:** OTA·다이렉트 등 멀티채널에서 재고가 어긋나면 오버부킹 → 보상·CS·신뢰 붕괴 (문제 후보 #1).
- **체크인 쪽:** 예약은 있어도 키/본인확인/객실 Ready가 안 되면 게스트가 문 앞에서 멈춤 → 무인 Activation 붕괴 (문제 후보 #2).

증상은 “문의 폭주·현장 출동”이고, 근본은 **판매 가능 여부(CMS·재고)** 와 **입실 가능 여부(체크인 readiness)** 가 하나의 Go/No-Go로 묶이지 않은 것.

### Opportunity

- **Activation:** 첫 숙박의 Aha = “앱으로 키 받고 바로 들어갔다.”
- **Revenue / Supply 신뢰:** 오버북·이중판매를 설계로 막아 점유·위탁 신뢰 유지.
- Plott OS 가치제안(호텔 대비 소수 인력)의 **최소 필수 축**이 CMS + 체크인이다. 프라이싱·주차는 그 위에 얹는 부가·최적화.

### Needs (JTBD)

| Who | JTBD |
|-----|------|
| 게스트 | 약속한 시간에 **막히지 않고** 방에 들어가고 싶다 |
| 운영 | 채널에 **팔아도 되는 재고만** 노출하고, 입실 전 이슈를 미리 잡고 싶다 |
| 오너 (간접) | 사고·보상 없이 점유가 안정적으로 나오길 원한다 |

### 5 Whys

1. 왜 게스트가 입실에 실패하나? → 키 없음 / 본인미확인 / 방 미배정·Dirty / 실방 부족.
2. 왜 실방이 없거나 미배정인가? → 채널에 이미 초과 판매됐거나, 호텔형 배정이 체크인 직전인데 Ready 객실이 없다.
3. 왜 초과 판매되나? → 채널별 재고가 중앙 규칙(ADR-001)과 동기화되지 않음.
4. 왜 동기화가 깨지나? → CMS·재고 코어가 “판매 모드 + 오버북 게이트”의 **단일 진실**이 아님.
5. **근본 원인:** **판매 가능(재고·CMS)** 과 **입실 가능(체크인 readiness)** 이 분리되어, 무인 환경에서 프론트 보완이 불가능함.

## 2. Stage & RARRA

| 항목 | 값 |
|------|-----|
| Stage | Traction (과제·프로토타입 / Pre-PMF 학습) |
| Bottleneck | **Activation** (체크인 Go) — 전제 조건으로 **Revenue 가드레일**(CMS·재고 정합) |
| Aha Moment | 체크인 시각에 앱에서 키를 받고 문에 들어가 성공 |
| North Star / KR | **체크인 성공률**(Go 상태에서 입실 완료) ↑ · **오버북 사고 건수**(실방 부족) → 0에 가깝게 |

**진단 순서:** Retention은 “입실 성공 경험” 없이는 성립하지 않음 → 이번 스콥은 Activation 병목을 직접 치고, CMS로 그 전제(팔린 예약이 실재하는 방)를 지킨다.  
Acquisition(유입·채널 확장)은 이번 정책 목표가 아니다.

## 6. Execute — 실험 설계

- **Hypothesis:** 판매 가능 재고(CMS·ADR)와 입실 readiness를 같은 Go/No-Go로 묶으면, 오버북·키 실패 시나리오를 프로토타입에서 **재현 전에 차단**할 수 있다.
- **Metric:** 시나리오 통과율 — (1) 게이트 위반 예약 거부 (2) No-Go 키 차단 (3) All-Go 체크인 성공.
- **Next action if true:** PRD → 프로토타입 구현 → HK SLA(#3) 얇게 연결 검토.
- **Next action if false:** readiness 항목이 過多인지 / 재고 모드 가정이 틀린지 분리 실험. 프라이싱·주차로 도망가지 않는다.

## 8. 가정 / 위험 가정

- 가정: 판매 모드는 ADR-001 — **특정방** / **호텔형 풀** 둘 다. 오버북은 호텔형만·기간·규모·비율 게이트.
- 가정: 체크인 readiness 최소 항목 = **본인확인 · 키 발급 가능 · 객실 Ready(및 호텔형이면 유닛 배정) · (선택) 결제 완료**.
- 가정: CMS MVP는 **1~N 채널 stub**이 중앙 재고 API를 읽고 쓰며, 채널별 임의 증감 금지.
- 가정: 어반스테이 실운영이 특정방/호텔형 중 어디에 가까운지는 ADR 미결 — 프로토타입은 **모드 스위치**로 둘 다 데모.
- 위험 가정 (#15): “Confirmed 예약이면 항상 방이 있다”를 깨지 않으면 체크인 UX만 예쁘게 만들어도 사고남.
- 검증 방법: 오버북·Dirty·미인증 시나리오를 테스트 케이스로 고정.

## 9. 도메인 정책 요약 (구현 전제)

### 9.1 CMS · 재고 (Plott OS 01 + PMS 코어)

1. **단일 진실:** `max_sellable` / 유닛 가능여부는 중앙 재고만 결정. 채널은 조회·예약 요청만.
2. **ADR-001 준수:** 특정방 = 오버북 0 · 예약 시 유닛 확정. 호텔형 = 타입 풀 · 게이트 통과 시에만 초과 · 유닛은 체크인 시 배정.
3. **게이트 수치:** `min_lead_days`, `min_capacity_for_overbook`, `overbook_rate`는 어드민 설정. 기본 보수적.
4. **동기 실패 시:** 판매 차단(닫기)이 열기보다 우선. 가정: stale이면 해당 날짜·타입 **판매 중지**.

### 9.2 체크인 (Plott OS 04)

1. **Check-in readiness = AND of Go flags.** 하나라도 No-Go면 키 미발급·입실 불가 안내.
2. **최소 Go flags (MVP):**
   - `identity_verified`
   - `payment_ok` (가정: 선결제 완료 또는 허용된 미수 없음)
   - `inventory_ok` (실방 존재 · 호텔형이면 배정 가능 유닛 ≥1 Ready)
   - `unit_assigned` (특정방은 예약 시 이미, 호텔형은 체크인 플로우에서)
   - `room_ready` (HK: Ready. Dirty/Cleaning이면 No-Go)
   - `key_issuable` (도어락 stub 성공)
3. **키는 Go 이후에만.** No-Go에서 키를내면 정책 위반.
4. **운영자 override**는 과제 MVP에서 최소화. 가정: 로그 남는 수동 override 1종만 허용 여부 — PRD에서 확정.

### 9.3 둘의 연결

```
채널 예약 요청
  → CMS/재고: ADR로 accept/reject
  → 예약 Confirmed
  → (입실 전) readiness 집계
  → All Go → 키 발급 → 체크인 성공
  → any No-Go → 키 차단 + 사유 노출(게스트·운영)
```

재고 사고는 체크인 직전에 발견해도 늦다. **CMS에서 막는 것이 1차, readiness는 2차 방어.**
